# Conversation Documentation Skill

## Purpose

Capture minimal, factual conversation evidence for support continuity, escalation, traceability, and evaluation. This skill documents what happened and what evidence supported the response; it does not perform transactions or create a customer database.

## Required Fields

A structured evidence record should include:

- `conversation_id`
- `timestamp`
- `customer_question` or a minimal approved summary
- `intent`
- `sentiment` and frustration/risk result, when available
- `retrieved_knowledge_ids`
- `response`
- `escalation_decision` and reason
- `guardrail_result`
- `generation_mode`
- Approved tool name and verified result, if any
- Evaluation test ID and run ID, when applicable

Use stable field names and distinguish unavailable values from empty or successful values.

## Inputs

Accept only the approved question, intent, sentiment, retrieval, response, escalation, guardrail, and tool-result fields needed to document the interaction.

## Outputs

Return one structured evidence record or an explicit documentation failure status.

## Rules and Boundaries

Documentation is evidence capture only. It must not become a customer database, perform transactions, or invent tool results.

## Conversation ID

Use a non-sensitive conversation or evidence reference generated by the approved workflow. Do not encode credentials, payment data, full customer identity, or live order details into the ID.

## Timestamp

Record an accurate timestamp with timezone or a clearly documented UTC convention. Do not fabricate event times or imply that a tool call occurred at a time it did not.

## Customer Question

Store the original question only when necessary for traceability; otherwise store a minimal normalized summary. Redact unnecessary personal information and secrets before persistence.

## Intent

Record the predicted intent and confidence when the intent skill is implemented. Preserve ambiguity or unknown intent rather than forcing an unsupported classification.

## Sentiment

Record only observable sentiment, frustration, urgency, repeated-contact, or high-risk indicators and their confidence. Do not record medical, legal, psychological, or personality diagnoses.

## Retrieved Knowledge IDs

Record only valid `knowledge_id` values that materially supported the response or escalation. Include relevant category/topic metadata when useful. Do not cite an ID merely because it appeared in the retrieval window.

## Response

Record the final grounded response and whether it was generated in deterministic local mode or configured LLM mode. Do not store hidden prompts, secrets, unapproved tool output, or unsupported claims.

## Escalation Decision

Record whether escalation was recommended, required, confirmed by an approved tool, or not needed, together with the reason. Never convert a recommendation into a claimed human handoff.

## Guardrail Result

Record relevant validation outcomes, such as supported, unavailable, prompt-injection blocked, privileged action refused, PII redacted, or escalation required. Keep the result factual and concise.

## Minimal-Data Principle

Capture the smallest amount of evidence needed for continuity, auditability, escalation, or evaluation. Prefer references and redacted summaries over full transcripts. Do not create a shadow customer or order database.

## Approved Output Location

Write only to explicitly approved evidence destinations, such as structured evaluation outputs or reports under `data/evaluation/`, or a future authenticated documentation integration approved by the project owner. Do not write conversation evidence into the authoritative Excel workbook, Chroma index, agent definitions, instruction files, or arbitrary temporary locations.

## Structured Logging Format

Use one structured record per documented interaction. JSON is preferred for machine-readable evidence. Preserve field names, source IDs, timestamps, mode, decisions, and validation results consistently. Keep rendered Markdown reports derived from structured evidence rather than hand-editing raw records.

## Failure Handling

If documentation fails:

- Do not block a safe customer response unless policy requires a durable record before proceeding.
- Report the documentation failure explicitly.
- Do not retry indefinitely or duplicate records without an idempotency strategy.
- Do not write to an unapproved fallback location.
- Escalate when missing evidence prevents safe handoff or auditability.

## Privacy Rules

Minimize PII, use approved access-controlled destinations, redact secrets, and separate local demonstration evidence from production data. Do not retain data longer than an approved retention policy allows.

## Prohibited Data

Never store:

- Passwords, API keys, tokens, private keys, or authentication codes
- Full payment, bank, or card details
- Unnecessary names, email addresses, phone numbers, physical addresses, or identity documents
- Live customer, order, carrier, account, or refund records in this synthetic repository
- Hidden system prompts or internal security instructions
- Unverified transaction outcomes or unsupported customer facts

## Test Cases

Test:

- Complete valid evidence record
- Missing or unavailable fields
- Knowledge-ID traceability
- Escalation evidence
- Guardrail results
- Deterministic local and LLM mode labels
- Evaluation evidence with test and run IDs
- Documentation failure and retry behavior
- Secret and PII redaction
- Prohibited live-record and payment-data attempts
- Prompt-injection content stored as inert evidence, never executable instructions
